# 08 · 登录注册与权限管理（新增，全员必读）

## 1. 一句话职责

给系统加账号：登录注册、密码加密、按角色分工放权——
每个班主任只能操作自己班的增删改查，别人的数据看得到也动不了。

Python 是正式实现（`backend/api/auth_api.py`、`backend/api/permissions.py`、
`backend/security.py`）；预览前端 `src/lib/auth-api.ts` 用同样的规则做了镜像，
方便不连后端也能演示完整流程。

## 2. 角色与权限一张表（就这一张，别再记别的）

| 角色 | 可以做的模块 | 范围 |
|---|---|---|
| admin 管理员 | 全部，含班级建档、老师建档、账号管理 | 全部班级 |
| head_teacher 班主任 | 学生、成绩、就业、班级维护 | **只限自己带的那个班** |
| teacher 授课老师 | 成绩 | 只限自己带的那个班 |
| employment 就业专员 | 就业 | 全部班级 |
| viewer 只读 | 无 | 只能看，任何写操作 403 |

代码里就是一张字典 `ROLE_RULES` + 一个函数 `check_permission(user, module, class_id)`，
两个判断：① 这个角色能操作这个模块吗？② 只能管自己班的话，class_id 是不是自己的班？

## 3. 接口一览

| 方法与路径 | 作用 | 谁能用 |
|---|---|---|
| POST `/api/v1/auth/register` | 注册账号 | 系统空库时任意（首号变管理员）；之后仅管理员 |
| POST `/api/v1/auth/login` | 登录，返回 token | 任意 |
| POST `/api/v1/auth/logout` | 退出登录，清空 token | 已登录 |
| GET `/api/v1/auth/me` | 查看当前登录用户 | 已登录 |
| GET `/api/v1/users` | 用户列表 | 管理员 |
| PATCH `/api/v1/users/{id}` | 改密码、角色、所属班级、启停 | 管理员 |

写操作（POST/PATCH/PUT/DELETE）都必须带 `Authorization: Bearer <token>`，
没带 401；越权 403。

## 4. 数据模型（users 表）

`username` 全表唯一、`password_hash`（bcrypt 加密）、`display_name`、
`role`、`class_id`（班主任/授课老师用）、`token`（登录令牌）、
`is_active`（0=停用后不能登录）+ 4 个公共字段（逻辑删除和时间戳）。

## 5. 每个接口的处理步骤

**注册**：① 账号重复 409 → ② 系统里一个账号都没有？第一个自动建成管理员；
已有账号则要求管理员登录（401/403）→ ③ 班主任/授课老师必须给班级，班级要存在（404）→
④ `hash_password` 加密后入库。密码永远不落明文、不回传。

**登录**：① 账号存在且未删（404，提示统一是"用户名或密码错误"）→
② `verify_password` bcrypt 校验（不匹配 400，同样提示）→
③ 停用账号 403 → ④ 生成随机令牌写回 `users.token`，返回 `{token, user}`。

**写操作权限**：每个写接口开头一行
`check_permission(current, "student", student.class_id)`。
比如班主任给别的班加学生 → 403「只能操作自己负责班级的数据」；
授课老师想建学生 → 403「当前角色（teacher）无权操作该功能」。

## 6. 安全细节（答辩讲得出）

- 密码用 bcrypt 加密（Python）、scrypt（预览镜像），只存哈希；
  bcrypt 上限 72 字节，所以接口限制密码长度 6–72。
- 登录失败统一提示"用户名或密码错误"，不告诉你到底是哪个错。
- 令牌是 48 位随机数，退出登录即清空，旧令牌立刻失效。
- 停用账号（is_active=0）后令牌查询直接查不到，等于强制下线。

## 7. 测试清单（tests/test_auth.py，25 条）

注册：首号变管理员、重名 409、密码过短 422、用户名过短 422、
班主任没班级 422、角色非法 422、匿名注册被拒 401。
登录：成功返 token、密码错 400、账号不存在 404、停用 403、
me 无令牌 401、假令牌 401、正常 me 200、退出后令牌失效。
用户管理：管理员建五种角色、非管理员建号 403、改密码后旧密码失效、
列表不返回 password_hash、无令牌写操作 401。
权限：班主任只管自己班（建学生 201 / 别班 403）、班主任不能删别班学生、
授课老师只在自己班录成绩、授课老师不能建学生、就业专员可跨班登记、
只读不能写、班主任转班需对目标班有权限。

## 8. 答辩话术

60 秒介绍：
> 我加了登录注册和权限管理。users 表存 bcrypt 加密后的密码，
> 登录发一个随机令牌，写操作都要求带令牌。
> 权限只有一张表两个判断：角色能不能操作这个模块、是不是自己班的数据。
> 比如班主任 head_teacher 只有 student/score/employment/class 四个模块，
> 且 class_id 必须是自己带的班，跨班一律 403。
> 测试 25 条，覆盖注册登录和五个角色的越权路径。

预判提问 1："为什么不用 JWT？"
> 基础版只需要"登录后凭令牌找人"，令牌存数据库最直白：
> 退出即失效、停用即下线，不用解释过期时间和密钥轮换。等上生产再换 JWT 也不用改业务代码。

预判提问 2："权限校验放哪里，为什么不是中间件？"
> 就放在每个写接口开头一行 `check_permission(...)`。
> 初级同学一眼能看到"这个接口谁能用"，比藏在中间件里好维护；
> 规则集中在一个字典里，改规则只改一处。

预判提问 3："前端挡住了，后端还需要校验吗？"
> 需要，而且以后端为准。前端只是体验优化，Postman 直接调接口一样要被 403 拦住。
> 这也是测试里专门有"绕过界面直接调接口"这类用例的原因。
