# 03 · 就业信息管理（成员 3）

## 1. 一句话职责

保存每个学生多段就业历史：谁、去哪家公司、什么岗、多少钱、什么时候拿 Offer。
新增不覆盖旧记录，改和删只影响当前这一条。

文件：`model/employment_record.py`、`scheme/employment_record.py`、
`dao/employment_record_dao.py`、`api/employment_record_api.py`，
测试 `tests/test_employment.py`（27 条）。

## 2. 接口一览（7 个核心 + 2 个前端扩展）

| 方法与路径 | 作用 |
|---|---|
| POST `/api/v1/employment-records` | 新增一段就业经历（返 201） |
| GET `/api/v1/employment-records` | 列表：学生编号/班级/公司/城市/岗/薪资筛 |
| GET `/api/v1/students/{id}/employment-records` | 学生就业历史（按开放日期排序） |
| GET `/api/v1/classes/{id}/employment-records` | 班级就业记录（按班级快照） |
| GET `/api/v1/employment-records/options` | 有效记录中的城市、岗位筛选项 |
| GET `/api/v1/employment-records/{id}` | 详情 |
| GET `/api/v1/employment-records/{id}/comparison` | 本条记录就业前后的岗位、薪资对比 |
| PATCH `/api/v1/employment-records/{id}` | 改当前一条 |
| DELETE `/api/v1/employment-records/{id}` | 逻辑删除当前一条 |

## 3. 请求体逐字段（EmploymentCreate）

必填：`student_id`、`company_name`、`salary_amount`（≥0）、`salary_period`
（MONTH/YEAR，只认这两个）。
可选：`employment_open_date`、`offer_date`、`employment_city`、`position`。
姓名和班级快照（`student_name_snapshot/class_no_snapshot`）**不许客户端传**，
服务端始终从学生当前档案填入。就业前快照（`previous_position`、
`past_salary_amount/past_salary_period`、`past_graduation_date`）可以由前端手动提交；
某字段未提交时服务端从该学生最近一条有效过往经历复制，显式 `null` 则表示本条不采用。
这些值只属于当前就业记录，之后不会跟随学生档案变化。

## 4. 每个接口的处理步骤

**新增**：① 学生存在未删（404）→ ② 学生所属班级必须存在，
取不到班级快照直接 404（快照是必填，不能写空）→
③ 组装落库，姓名/班级快照只复制一次。

**编辑**：只取本次提交字段；离开就业时间/ Offer 时间都改时用“改后值”复检；
日期关系不对 400；已有 Offer 时不能只清空开放日期 400。

**删除**：查可见性 → 打标记 → 兄弟记录不受影响。

**详情与对比**：`annualized_salary` 现场计算（MONTH×12、YEAR 本身）；
对比接口再算年薪增减、折合月薪；无历史薪资就说“暂无基准”，
不把缺失当 0 钱误导。

## 5. 日期三条规则（2026-10 加严，前后端一致）

1. Offer 有值但开放日期为空 → 422（新增）/400（修改），提示
   “就业尚未开放，填写 Offer 日期之前请先填写就业开放日期”。
2. Offer 早于开放日期 → 422/400，提示“Offer 日期不能早于就业开放日期”。
3. 同一天可以。
前端表单实时报红、输入框的 min/max 互相约束，保存前再兜底；
后端重复校验，绕过页面直接调接口也拦得住。

## 6. 业务规则和边界

- 班级口径统一按历史快照 `class_no_snapshot`：筛选、时长、转班都不影响历史。
- 学生改名后旧记录快照不变，这是故意的，不是 Bug。
- 薪资筛选兼容三种口径：`min/max_salary` 默认按原始值（可配 `salary_period`）；
  配 `salary_basis=MONTH/YEAR` 时跨周期折合为月薪/年薪；
  `min/max_annualized_salary` 继续按年薪等价值筛选。
- 毕业年限用 `past_graduation_date` 动态推导；没填就不参加
  `min/max_graduation_years` 筛选。
- 已删除学生的就业记录普通查询不可见（详情 404）。

## 7. 测试清单（27 条重点）

新增：月薪年薪共存、年薪等价值算对、快照写入正确、学生改名后快照不变。
日期：Offer 早于开放 422、Offer 只有日期没有开放 422、同日 OK、
修改时只清开放日期 400。
独立性：两条记录增删互不影响、学生历史排序按开放日期。
筛选：城市/岗位/班级快照/原始薪资/年薪等价值/学号。
可见性：学生删除后详情 404、列表 0 条。

## 8. 答辩话术

60 秒介绍：
> 我负责就业信息管理。一名学生可以有多段就业记录，互不覆盖。
> 三个关键点：第一，年薪等价值统一口径——月薪乘 12 再和年薪比，
> 展示保留原始口径；第二，姓名班级快照创建时钉死，
> 学生后来改名转班不污染历史统计；第三，2026 年补了日期顺序：
> 没开放就业服务就不能填 Offer，Offer 也不能早于开放日期，前后端都拦。
> 测试 27 条，重点是日期三规则、多段独立和快照不变。

预判提问 1：“就业记录多了几条，统计怎么才不重复？”
> 每条都是独立段。班级人数用 COUNT DISTINCT 学生；
> 平均求职周期只取有开放和 Offer 两个日期的记录。
> 所有统计还要排除学生或记录被删除的。

预判提问 2：“为什么不直接把年薪存库？”
> 存一份会和原始口径不一致的风险。原始金额加周期才是真相，
> 年薪等价值每次现算，口径永远统一，排序筛选响应都能用。

预判提问 3：“他换了班，以前那段就业算哪个班？”
> 算就业记录快照里的班，也就是他当时所在的班。
> 这正是要快照的原因，不然历史就业率就会跟着转班漂移。
